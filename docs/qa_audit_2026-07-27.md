# Awaken — End-User QA Audit & Remediation Plan

**Date:** 2026-07-27 · **Branch:** `redesign-afsan` · **Scope:** all user-facing
Flutter code under `lib/` (screens, widgets, cubits, theme), plus lifecycle and
native-integration touchpoints.

**Baseline at audit time:** `flutter analyze` → *No issues found*.
`flutter test` → *All tests passed* (57 tests). Every finding below is a
behavioral/UX defect that static analysis and the current suite do not catch.

## 3. Non-breaking remediation plan

### 3.1 Safety strategy & guardrails

**Invariants that must not change.** These are load-bearing per `CLAUDE.md` and
in-code post-mortems; every fix below is written to leave them untouched:

1. `androidStopAlarmOnTermination: false` (`alarm_repository_impl.dart:125`).
2. The ring screen stays an overlay in `MaterialApp.builder`, never a route
   (`app.dart:59-63`).
3. `verificationInProgress` continues to make the overlay step aside
   (`app.dart:186`), and lockdown stays keyed off `ringingAlarm` alone.
4. `PopScope(canPop: widget.isPreview)` on the ring page — a *real* alarm must
   never be back-dismissible.
5. The map widgets are built exactly once and mutated imperatively; nothing may
   move `MapLibreMap` inside a `BlocBuilder`.
6. `ACCESS_BACKGROUND_LOCATION` stays undeclared.
7. Public widget constructors (`AdaptiveNavScaffold`, `StatTile`,
   `ProfileAvatarButton`, `ExpressiveFlower`, `AlarmRingPage`,
   `VerificationPage`, `TerritoryCaptureSheet`, `WorkoutCelebrationSheet`) keep
   their current required/optional parameter shape. New parameters are optional
   with defaults matching today's behavior.
8. No cubit's public method signatures or state class fields are removed; only
   additive fields (with defaults) are permitted.

**Tests to write *before* touching code** (each must fail against `HEAD`, then
pass after the fix):

| Test file | Guards |
|---|---|
| `test/features/alarm/schedule_sheet_recurrence_test.dart` | C-03 — first occurrence of a `{Saturday}` alarm created on a Monday lands on Saturday. Pure unit test against a new `firstOccurrence()` helper. |
| `test/features/profile/avatar_initial_test.dart` | C-02 — empty-string display name yields a fallback initial, no `RangeError`. |
| `test/features/squad/squad_error_recovery_test.dart` | C-01 — after a failed `joinSquad`, the error view exposes both retry paths and returns to `noSquad`. |
| `test/features/alarm/alarm_ring_double_tap_test.dart` | C-04 — two taps in one frame produce exactly one navigation. |
| `test/features/territory/active_run_abandon_confirm_test.dart` | J-01 — back gesture and Stop both raise a confirm dialog; declining keeps the run alive. |
| `test/features/alarm/reliability_test_cleanup_test.dart` | J-02 — the test alarm is cancelled on pass, on timeout, and on `dispose`. |
| `test/features/onboarding/onboarding_overflow_test.dart` | J-06 — pump at `TextScaler.linear(2.0)` on a 320×568 surface; assert no overflow exception. |
| `test/features/territory/active_run_overflow_test.dart` | J-07 — same technique. |
| `test/a11y/tap_target_test.dart` | A-02/A-03/A-04 — `meetsGuideline(androidTapTargetGuideline)` on the schedule sheet, page headers, and `ExpressiveSwitch`. |
| `test/a11y/contrast_test.dart` | A-01/A-05 — `meetsGuideline(textContrastGuideline)` on Home and Alarms in light theme. |

Extend `test/features/shell/app_shell_page_test.dart` and
`test/features/alarm/alarm_list_page_test.dart` rather than replacing them —
they are the regression net for the nav shell and list rendering.

### 3.2 Sequential fix execution

Ordered Critical → Major → Minor → Polish, grouped by feature domain so each
step touches one directory and can be reviewed and reverted independently.

---

#### Step 1 — Alarm domain, critical (C-03, C-04, J-12)

1. **C-03.** Add to `AlarmSchedule` (`alarm_schedule.dart`), alongside the
   existing `nextOccurrenceAfter`:
   ```dart
   /// First fire time for a newly created alarm: [nextOccurrenceAfter] for a
   /// recurring alarm, else the next today/tomorrow slot at that time-of-day.
   static DateTime firstOccurrence({
     required DateTime timeOfDay,
     required Set<int> recurringDays,
     required DateTime from,
   });
   ```
   In `_ScheduleSheetState._targetDateTime` (`alarm_list_page.dart:686`),
   delegate to it, passing `_days`. Keep the one-shot branch byte-identical so
   non-recurring behavior does not move. `_formatTargetSummary` (`:701`) gains a
   weekday name when `recurringDays` is non-empty ("Alarm set for Saturday at
   7:00 AM").
2. **C-04.** In `_AlarmRingPageState`, add `bool _startingWorkout = false`;
   first line of `_startWorkout` becomes `if (_startingWorkout) return;` and it
   is set synchronously *before* `setState`, cleared in the existing `finally`
   next to `setVerificationInProgress(false)`. No signature change.
3. **C-04 hardening.** Replace `navigatorKey.currentState!` (`:78`) with a
   null-checked local; on null, clear `_workoutStarted` and return rather than
   throwing on the dismissal path.
4. **J-12.** `_ScheduleSheetState` gains `bool _saving`; the Save
   `GestureDetector` no-ops while true and shows a small inline spinner.
   `onSchedule` becomes `Future<void> Function(...)` so the sheet can await it
   before popping — `_showScheduleSheet`'s body already returns a `Future`, so
   only the typedef changes.

Verify: `flutter analyze && flutter test` (steps 1–4 tests + existing alarm
suite). Manual: create a Saturday-only alarm on a weekday, confirm the summary
and the resulting list row.

### 3.3 Validation & verification protocol

Run after **every** step, not only at the end:

```bash
flutter analyze
```

```bash
flutter test
```

After any change touching `@injectable`/`@lazySingleton`/Drift tables:

```bash
dart run build_runner build --delete-conflicting-outputs
```

Targeted suites while iterating on one domain:

```bash
flutter test test/features/alarm test/features/squad test/features/territory
```

Device verification — static analysis cannot confirm any of these, and the
alarm path in particular has already been empirically wrong more than once:

```bash
flutter run --flavor dev -t lib/main_dev.dart
```

1. Schedule a recurring alarm for a single future weekday; confirm the first
   ring lands on that weekday (C-03).
2. Lock the screen, let a real alarm fire, double-tap "Start workout"; confirm a
   single camera session (C-04) and that the overlay/lockdown behavior is
   unchanged.
3. Force-kill the app, wait for a scheduled alarm; confirm it still rings
   (guards invariants 1 and 2).
4. Sign in with an account whose display name is empty; open Profile (C-02).
5. Join a squad with a bad code, then a good one, without restarting (C-01).
6. Start a run, press back mid-run, decline the dialog, continue, capture
   (J-01).
7. Set system font size to maximum; walk Home → Alarms → schedule sheet →
   Territory → Active run → Squad → Profile → onboarding, watching for overflow
   stripes (J-06, J-07, A-06).
8. Enable "Remove animations" in system settings; confirm the ring bell, status
   banner, and run dot all sit still (N-12).
9. Toggle light/dark; confirm every `ExpressiveFlower` badge is visible in light
   mode (A-05).
10. Run the reliability self-test twice; confirm no stray alarms remain in the
    list afterward (J-02).
